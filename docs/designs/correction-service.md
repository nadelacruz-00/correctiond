## Problem Statement

No usable system-wide autocorrect exists on Linux/Wayland. The user types fast
(Colemak primary, QWERTY secondary) across terminals, browsers, and editors on
GNOME 50.1/Wayland and wants typos fixed silently, phone-keyboard style, with
the tool learning their personal vocabulary and slip patterns — fully local,
network-off, and non-intrusive. Goal: personal daily driver first, open source
second.

Environment facts (verified live): GNOME Shell 50.1, Wayland, IBus 1.5.34
running, layouts `us+colemak` + `us`, terminal is Ptyxis (VTE/GTK4), hardware
is a CPU-only aarch64 machine.

## What Makes This Cool

- **First of its kind.** Every existing Linux option is either a suggestion
  list you must pick from (ibus-typing-booster), X11-only (autocorrect-linux),
  or a clipboard+LLM hack (ollama-autocorrect-git). Nobody has shipped silent,
  phone-keyboard-style correction on Wayland. The IBus surrounding-text API
  supports it; it's just unbuilt.
- **It learns *you*.** Layout-aware error models: a Colemak typist's finger
  slips are different letters than QWERTY's, and the model knows which layout
  is active. Your jargon, usernames, and identifiers enter your personal
  vocabulary so they are never "corrected."
- **Reverts teach it.** In silent-path apps, one backspace immediately after
  an auto-fix undoes it and blacklists that correction pair. The tool gets
  quieter and smarter the more you type.
- **Zero network, near-zero battery.** Statistical models (edit distance +
  frequency + bigram context) are expected to decide a correction in well
  under a millisecond on this hardware — to be validated by a corelib
  benchmark; the binding criterion is the success-criteria p99 < 10 ms. No
  LLM, no daemon spinning.

## Constraints

- **Wayland security model:** a GNOME Shell extension cannot see or rewrite
  keystrokes in other apps. The only sanctioned system-wide interception point
  is the input method framework (IBus). This forced the architecture.
- **IBus surrounding-text gotchas** (all externally documented, treated as
  first-class design constraints):
  - delete_surrounding_text/commit_text ordering bug in some clients
    (ibus#2570) — produced interleaved text in gnome-text-editor/gtk4-demo.
  - On Wayland without `GTK_IM_MODULE=ibus`, surrounding-text offsets can be
    octets, not characters.
  - The first surrounding-text request after engine activation can fail;
    request once at enable time as a warm-up.
  - Not all clients support surrounding text at all → a per-app fallback
    strategy is required (see Recommended Approach).
- **Hardware:** aarch64 CPU-only; correction must be O(word) with precomputed
  indexes; no per-keystroke model inference.
- **Non-intrusive:** silent mode shows nothing — no popups, no candidate
  lists. Preedit-based fallback (visible underline while composing) is a
  per-app degradation, not the default.
- **Terminal safety:** never alter command-like tokens. VTE (Ptyxis) reports
  IBus input purpose TERMINAL; password fields report purpose PASSWORD
  (hard off); fields with NO_SPELLCHECK hint are off.
- **Multi-layout (user requirement):** per-layout key-geometry tables for
  `us+colemak` and `us`, switching with the active input source.
- **OSK integration (user requirement):** the user runs GJS OSK
  (`gjsosk@vishram1123.com`) on this tablet. When the OSK is visible, typing
  is QWERTY-rendered touch input — tap-geometry errors, not Colemak physical
  slips — so the engine must switch to the QWERTY/OSK error model while the
  OSK is shown and back when it hides. Integration must require **no changes
  to gjs-osk code**: detection happens from the companion Shell extension,
  which runs in the same Shell process and observes gjs-osk's keyboard actor
  visibility from outside (the same sibling-extension pattern as the user's
  own gjsosk-theme-sync extension).

## Premises (agreed D3)

1. Core deliverable is an **IBus engine**, not a GNOME Shell extension; a thin
   Shell indicator is the on/off UI and the focused-app identity supplier.
   Portability caveat: the engine architecture runs on any distro/desktop
   with IBus, but in v1 corrections fire only where the app can be
   identified, and the wm_class supplier is a GNOME Shell extension — so on
   non-GNOME desktops v1 is learn-only pass-through until an equivalent
   supplier exists. The open-source portability claim is architectural, not
   v1-functional.
2. "Local AI that learns" = lightweight statistical models (personal
   vocabulary, bigram context, layout-aware edit distance, revert learning) —
   not an LLM.
3. Correction fires silently at word boundaries via surrounding-text, with
   the documented IBus gotchas handled; backspace-revert undoes and teaches.
4. Prose-awareness decides where silence is allowed: terminals get
   conservative prose-aware mode; prose fields get full silence; all data
   stays local.
5. Doing nothing is a real loss: no working alternative exists on Wayland.

## Approaches Considered

- **Approach A: Quiet Fix (Python IBus engine, minimal viable)** — ruled out
  by user in favor of the long-term architecture; Python packaging also
  weaker for the open-source goal.
- **Approach C: Typing Twin (learning-as-the-product: git-history bootstrap,
  stats, ghost text)** — deferred, not rejected; it is additive on top of B.
  Its best ideas survive as Open Question 5 (corpus bootstrap) and the
  control-plane stats query; neither is a committed milestone.

## Recommended Approach: B — Correction Service (Rust engine + daemon)

Chosen by user (D5), with multi-layout support promoted to a core requirement.

**Components:**

1. **`corelib` (Rust library, no IBus dependency)** — the brain, fully unit-
   testable offline:
   - Tokenizer + word-boundary detection (space/punctuation triggers).
   - Candidate generation: SymSpell-style precomputed deletes over a base
     dictionary (Hunspell wordlists) merged with the personal vocabulary.
   - Scoring: layout-aware weighted Damerau-Levenshtein (per-layout key
     adjacency tables for Colemak and QWERTY, plus a third **OSK tap table**:
     QWERTY geometry with touch fat-finger weighting — neighboring-key
     confusion dominates over transpositions) × personal word frequency ×
     word-bigram context probability. The active table is chosen by engine
     variant, overridden to the OSK tap table whenever `osk_visible` is true.
   - Confidence policy: correct silently only above threshold; below it, do
     nothing (silent mode never asks).
   - Prose/command classifier for terminal mode, computable from the engine's
     own key stream alone (no line-position reads): a correction in a
     terminal-purpose context fires only when ALL hold: (a) the token is
     purely alphabetic, lowercase or Capitalized, ≥ 4 chars, and never
     contains `/ - _ . ~ $ =` or mixed case; (b) the engine's **prose-run
     counter** is ≥ 2 — i.e., at least two clean prose words were COMPLETED
     before the candidate token; the candidate itself never counts toward
     the threshold. Any line-editing or
     navigation key (Tab, arrows, Home/End, Ctrl/Alt combos, Delete, Ctrl-W,
     Ctrl-U, history recall) resets the prose-run counter to zero, so command
     editing and completion never qualify; correction stays suppressed until
     two clean prose words are observed again. This drops the unobtainable
     "first token of a line" rule in favor of inputs the engine actually has.
2. **`engine` (Rust binary)** — IBus engine speaking the IBus D-Bus protocol
   via zbus (no maintained high-level Rust IBus crate is assumed; the engine
   implements `org.freedesktop.IBus.Engine` directly — this plumbing is the
   known cost of Approach B).
   - Maintains an internal buffer of the word being typed from
     process_key_event, so correction does not depend on reading surrounding
     text (only on deleting it).
   - **Buffer invalidation (safety rule: any desync signal suppresses the
     pending correction and clears the buffer):** the word buffer and the
     prose-run counter reset on focus_in/focus_out, reset(), any
     set_cursor_location change not caused by the engine's own commits, any
     navigation or editing key (arrows, Home/End, PgUp/PgDn, Delete, Tab, and
     all Ctrl/Alt/Super combinations), and any key the engine does not
     recognize as printable input — with one exception: **mid-word Backspace
     pops the last character from the word buffer** and the word stays
     correction-eligible; Backspace invalidates only when the buffer is
     empty, and the post-correction revert window consumes Backspace before
     this rule applies. Paste by mouse middle-click produces no
     key event, so as a second line of defense the engine **verifies before
     deleting**: when surrounding text is available, the characters preceding
     the cursor must exactly equal the buffered word, otherwise the engine
     does nothing.
   - At word boundary: if confident (and verification passed where
     available), delete_surrounding_text(len) + commit_text(fixed + boundary
     char); the warm-up surrounding-text request is made once at engine
     enable.
   - **Octet-offset mitigation:** v1 silently corrects only words whose
     original and corrected forms are pure ASCII, where byte length equals
     character length, so the octet-vs-character ambiguity cannot delete the
     wrong span; non-ASCII words are never silently corrected in v1. Combined
     with verify-before-delete, a wrong-span delete requires two independent
     failures.
   - **Per-app capability table and app identification:** IBus does not hand
     engines a client app identity, so the focused app's wm_class is supplied
     by the GNOME Shell indicator extension over the control-plane D-Bus
     interface (promoted from "later" to a v1 component for exactly this
     reason). The capability table and the correction allowlist key on
     wm_class. **When the app cannot be identified** (extension not running,
     non-GNOME desktop), the engine performs no corrections at all —
     pass-through only, observing vocabulary for learning. This is the
     genuinely conservative choice: surrounding-text verification is a
     read-only check and cannot protect against the ibus#2570 ordering bug,
     which corrupts text during the delete+commit itself, and without
     wm_class neither the capability table nor the allowlist can be
     consulted. Apps where
     delete_surrounding_text is broken (ordering bug) are listed in the
     capability table and degraded to a preedit fallback (compose the word in
     preedit, commit corrected at boundary — typing-booster's reliable path)
     or to pass-through.
   - **Revert mechanics, per mode.** Silent path: after an auto-fix the
     engine remembers (original, corrected, boundary). If the very next key
     is Backspace, the engine consumes it, performs
     delete_surrounding_text(len(corrected) + 1) and commits
     original + boundary — one backspace restores the original text,
     boundary char included, and records the blacklist pair. The revert
     delete obeys the same verify-before-delete rule as correction: when
     surrounding text is available, corrected + boundary must precede the
     cursor; on mismatch the engine deletes nothing but still records the
     blacklist pair. Preedit
     fallback: delete_surrounding_text is unavailable there by definition, so
     single-key revert does not exist; instead the engine learns from manual
     reverts: the (original, corrected, boundary) tuple survives Backspace
     presses; if the user backspaces at least len(corrected) + 1 times
     (reaching past the correction point) and then retypes original followed
     by a boundary, the pair is blacklisted. The window closes on any
     invalidation event other than Backspace, or at the next word boundary.
     The revert success criterion applies to silent-path apps only.
   - Content-type handling: purpose TERMINAL → prose-aware mode; PASSWORD/PIN
     → hard off; NO_SPELLCHECK hint → off.
   - **Multi-layout mechanism:** the component XML registers two engine
     variants, one with layout="us(colemak)" and one with layout="us".
     GNOME's input-source switcher (Super+Space) then switches between them
     exactly like ordinary keyboard sources, and IBus applies the matching
     XKB layout for whichever variant is active. Each variant binds its own
     key-adjacency table. There is no engine-side keycode translation and no
     "following" of a separate source.
3. **Learning store** — SQLCipher-encrypted SQLite at
   `~/.local/share/correctiond/` (0700 dir, 0600 files): personal vocabulary
   with frequencies, accepted/reverted correction pairs per layout, bigram
   counts. Pruned and size-capped. Nothing ever leaves the machine. Served
   from memory on the typing path; persisted write-behind. See "Security:
   data at rest" below.
4. **Control plane** — small D-Bus control interface (pause/resume, per-app
   mute, stats query) + GSettings schema for thresholds and mode defaults.
5. **GNOME Shell indicator extension (thin, v1 component)** — quick toggle,
   per-app mute, last-correction peek, and the supplier of the focused app's
   wm_class to the engine over D-Bus (see app identification above). The
   stock IBus panel still provides engine switching.
   **OSK integration (no gjs-osk changes):** the extension locates gjs-osk's
   keyboard actor in the Shell scene graph and connects to its
   `notify::visible` (plus extension enable/disable state), publishing
   `osk_visible` over the same control-plane D-Bus channel as wm_class. While
   `osk_visible` is true the engine scores with the OSK tap table; when it
   returns false the active engine variant's physical table resumes.
   Optionally (GSettings toggle, default on): the extension also switches the
   active input source to the QWERTY engine variant when the OSK appears and
   restores the previous variant when it hides, so gjs-osk's QWERTY key
   injection always lands on a QWERTY mapping. If gjs-osk is absent or the
   actor cannot be found, `osk_visible` stays false and nothing else changes.

**IBus integration detail:** the two engine variants replace the user's plain
XKB sources in the input-source list. "Pass-through" means the engine returns
every key event unhandled (process_key_event returns false) so the event
reaches the app exactly as plain XKB typing would — the engine only observes
the stream and acts at word boundaries. It never translates keycodes itself.
This pass-through-first design is also the safety default: any uncertainty →
do nothing.

## Security: data at rest

Added after the /cso pre-implementation audit (2026-11-04), which found that
the learning rule would persist secrets typed outside password fields and that
development logging would put keystrokes in the journal. Practices, in order
of importance:

1. **Collect less.** Learn only word-shaped tokens (letters only, 3–24 chars,
   no digits/symbols/mixed case). Never learn in terminals: a passphrase
   typed at a hidden `sudo`/`ssh` prompt looks like prose. Treat DIGITS,
   NUMBER, PHONE, URL, EMAIL, PASSWORD and PIN fields, and fields with the
   NO_SPELLCHECK or PRIVATE hint, as fully off (no correction, no learning).
   This supersedes the older PASSWORD/PIN-only content-type bullet above.
   Write a word to disk only on its second sighting. Residual risk: a
   letters-only passphrase typed into a field that reports no sensitive
   purpose can still be learned; encryption covers that case.
2. **Encrypt what remains.** SQLCipher with a random 256-bit raw key (AES-256
   pages, HMAC-SHA512 page authentication). A raw key skips PBKDF2, so opening
   costs nothing extra. Never create a plaintext fallback.
3. **Keep the key in the login keyring.** Generated from the OS CSPRNG,
   stored as a Secret Service item in the default (login) collection, which
   gnome-keyring unlocks with the login password through PAM. The engine
   never asks to unlock and never shows a prompt: if the keyring is locked or
   not running yet, learning continues in memory and attaches later.
4. **Keep crypto off the typing path.** Lookups read in-memory maps; disk
   writes are batched every 30 s and on focus-out/exit. Verified hardware
   support on this device: ARMv8 AES, PMULL, SHA2 and SHA512 instructions,
   which OpenSSL uses automatically. Expected cost: background flushes only;
   correction latency unchanged.
5. **Leave no side copies.** No typed content or key material in logs;
   tracing is opt-in, writes key classes only, to a 0600 file. The process
   sets PR_SET_DUMPABLE=0 (no ptrace) and RLIMIT_CORE=0 (no core files), and
   the package ships an apport ignore entry, because on this machine
   (`fs.suid_dumpable=2`) apport would otherwise still save a full memory dump
   to `/var/crash`. Databases that the key cannot open are quarantined
   (renamed), never deleted; I/O errors and busy files are retried, never
   quarantined.
6. **Give the user an off switch for the data.** "Forget learned words"
   deletes the database and the keyring item; the next start uses a fresh key.
7. **Authenticate the control plane.** Only the process owning
   `org.gnome.Shell` may set focused app, OSK state, enablement or purge.

**What this protects:** backups (for example a backup tool that includes `$HOME`;
the key's keyring file is itself encrypted with the login password), a
stolen device without full-disk encryption, and other local users, but only as
strongly as the login password: an empty-password login keyring stores the
key effectively in plaintext. **What it does not:** malware already running as the user, which can request the key
from the Secret Service. Full-disk encryption (LUKS) is the OS-level
complement and is recommended separately.

## Eng review additions (2026-11-04, binding)

Decisions taken in /plan-eng-review; the implementation plan's Decision ledger holds the full records.

- **English word source (D3):** known English words come from SCOWL (`/usr/share/dict/american-english`), ranked by the en_50k frequency counts; this supersedes "Hunspell wordlists" above.
- **Languages (D4):** Tagalog and Waray-Waray are first-class. Lexicons are data: a `[[languages]]` list in config.toml (English built in; Tagalog and Waray built locally from Leipzig Corpora frequency lists by `scripts/build-lexicon.py`, never shipped). A word in any lexicon or in personal vocabulary is never corrected. Corrections are restricted to the sentence's dominant language (majority of the last 4 known words by primary language; none ⇒ all languages with a stricter margin). Adding a language is one lexicon file plus one config entry. v1 lexicons are ASCII-only (TODOS.md).
- **Slip learning (D8):** personal slip patterns are learned only from the user's own mid-word fixes (backspace a letter, type a different one), per layout, and lower that substitution's cost; never from autocorrect's own accepted fixes. Vocabulary is keyed by word only.
- **Vocabulary import (D7):** a documented standard file format, "correctiond vocab v1" (`*.vocab.tsv`), accepted by the engine (`ImportVocabulary` D-Bus method, `engine import FILE`), re-validated with the same learnable-token rules, de-duplicated by file hash. A Facebook Messenger JSON converter is a separate tool under `importers/messenger/`, not bundled with or shipped in the app; it keeps only the user's own messages.
- **IBus layer (D2):** librush is a reading reference only, not a dependency.
- **License (D6):** MIT OR Apache-2.0.
- **Verification (D9, D10):** a python-gi golden for the IBusText structure and a headless end-to-end test through a real ibus-daemon, run in CI.
- **Index (D11):** SymSpell prefix length 7 with hashed keys, ≤ 32 MiB for English.

## Success Criteria

- Transposed/misspelled words are fixed silently at word boundary in Firefox,
  GTK apps, and Ptyxis prose contexts; p99 correction decision < 10 ms.
- With GJS OSK visible, corrections use the QWERTY/OSK tap model (and the
  QWERTY variant when auto-switch is on); hiding the OSK restores the
  physical Colemak model automatically, with no gjs-osk modifications.
- Zero corrections of commands, paths, flags, or identifiers in the terminal
  over a week of daily use.
- In silent-path apps, a single backspace reverts a fix; a reverted or
  manually-reverted pair never fires again in any app.
- Personal vocabulary visibly grows (new jargon stops being "corrected"
  within one occurrence of a revert or two sightings of the word).
- Verifiably network-off: the process opens no sockets other than the session
  D-Bus (checkable with `ss`/lsof).
- No measurable idle CPU; battery impact indistinguishable from baseline.

## The Assignment

Before writing any engine code, spend 30 minutes proving the load-bearing
primitive on your actual machine — specifically the
delete-surrounding-text-on-COMMITTED-text path this engine will use, not the
preedit path. Install `ibus-typing-booster`, open its setup tool and enable
the **reopen-preedit option** (the setting that lets Backspace pull an
already-committed word back into preedit via surrounding text +
delete_surrounding_text). Then in Ptyxis, Firefox, and gnome-text-editor:
type a word, press space, and confirm it is committed (underline gone); press
Backspace. Record per app: (a) does the committed word re-enter preedit
intact and recommit correctly, with no interleaved or duplicated characters
(that is delete_surrounding_text working on committed text), and (b) does
Ptyxis suppress the IME or change typing-booster's behavior (evidence of a
terminal input purpose). If the reopen option is absent in your
typing-booster version, note that and stop — the matrix then needs a
different probe, which is a design input itself. That 30-minute matrix
decides how big the preedit fallback has to be — the one thing this design
cannot know from documentation.

### R3-1 — consistency (blocking)

**Problem**

> The new unidentified-app rule contradicts Premise 1. Premise 1 still claims as a side effect that the engine 'works on any distro/desktop running IBus — wider than GNOME', but the changed text now commits that on a non-GNOME desktop (or whenever the extension is not running) 'the engine performs no corrections at all — pass-through only'. The sole wm_class supplier in the design is the GNOME Shell indicator extension, and no alternative identification mechanism for other desktops exists anywhere in the document, not even as an Open Question. So the product's core function — correction — is now GNOME-only by construction, while the agreed premises present wider-than-GNOME operation as a benefit of the IBus-engine choice. Before this change the claim was partially true (unidentified apps still received some corrections); the changed text exposed the contradiction.

**Remedy**

> Reconcile the two statements: qualify Premise 1 (e.g., 'runs anywhere IBus runs, but silent correction currently requires the GNOME indicator as wm_class supplier; other desktops are pass-through/learning-only'), and optionally add an Open Question or later milestone for a non-GNOME wm_class supplier (e.g., a KDE/wlroots equivalent or manual per-session override).

### R3-2 — clarity (minor)

**Problem**

> Persisting from R2-3: the silent-path revert performs delete_surrounding_text(len(corrected) + 1), but the design still does not say whether the verify-before-delete rule also applies to this second delete. The correction path was given a two-independent-failures guarantee; the revert path is silent about it.

**Remedy**

> State whether the revert delete re-verifies surrounding text (corrected + boundary preceding the cursor) and what happens when verification fails or surrounding text is unavailable.

### R3-3 — clarity (minor)

**Problem**

> Persisting from R2-4: Backspace is still not named in the buffer-invalidation key list, and mid-word Backspace falls under 'any key the engine does not recognize as printable input', which clears the whole buffer. Read literally, any word in which the user fixes a typo mid-word by backspacing is never eligible for correction, and the design does not say which behavior is intended.

**Remedy**

> Specify mid-word Backspace semantics: pop the last character from the word buffer (keeping correction eligible) or clear the buffer, and note the interaction with the revert path where Backspace is consumed.

### R3-4 — completeness (minor)

**Problem**

> Persisting from R2-5: preedit-fallback manual-revert learning ('observed from the key stream') still has no stated mechanism. It requires tracking state across a run of Backspaces and a retype, yet the invalidation rules reset engine state on non-printable keys, and nothing defines how the engine matches the deleted span to the remembered corrected word or how long the observation window lasts.

**Remedy**

> Sketch the manual-revert detector: what state survives the Backspace run (the remembered (original, corrected) pair), the matching rule (N backspaces covering corrected+boundary followed by retyping original), and when the window closes.

### R3-5 — consistency (minor)

**Remedy**

> Either add corpus bootstrap and a stats view as explicitly optional milestones in Next Steps, or soften the claim to say they survive as an open question and a control-plane query.

### R3-6 — feasibility (minor)
