## Problem Statement

correctiond never corrects a word that is in a lexicon or in personal vocabulary,
but the user's real chat language is not covered. A sizeable share of the learnable
words in the user's own Messenger messages is in no list. The most-used missing words
are everyday Waray/Bisaya, slang, and apostrophe-free English (dont, thats, didnt).
The Waray list was built from Wikipedia, much of it bot-written species articles, and
lacks chat Waray. Goal: import the export so the user's chat voice is never
"corrected" and rebuild the Tagalog and Waray lists from conversational text,
with every change measured instead of guessed. Typing slips from the chats come
last, only if measured to help.

Export facts (the real counts are deliberately left out of this public copy):
- The export is a set of zips, almost all media. A download may be incomplete
  (a 0-byte zip plus a `.part`).
- Message JSON sits in several folders (inbox, e2ee_cutover, archived_threads,
  e2ee_cutover_archived). All use the classic layout (`sender_name`,
  `timestamp_ms`, `content`, attachment keys), which the existing importer reads.
  Extracted to `~/Downloads/messenger-json/` (mode 0700).
- The e2ee_cutover threads rarely share participant sets with inbox threads, so
  double counting is negligible.
- About 1% of messages show Meta's latin-1 mojibake; a few hundred are Messenger
  notices ("You joined the video call"); some own texts sit on photo, call, share
  or unsent messages.
- Learnable tokens are 3-24 letters or apostrophes, starting with a letter,
  lowercase or Capitalized, as in `learnable()`. Not learnable: 1-2 letter
  tokens, ALL CAPS, other mixed case or symbols, digits, emoji, URLs, accented
  letters.
- Own tokens fall into three buckets by list: English only, Tagalog and/or Waray
  (alone or with English), and in no list. Many out-of-list words are stretched
  spellings (yesss, okiiii).
- Some repeated out-of-list words are one edit from a much more common word, but
  that test mislabels real Waray words (kadto/adto, utod/upod, kanay/anay), so
  letter-distance typo filtering is unreliable here.
- The user's own "*word" correction messages are mostly sent within 2 minutes of
  an earlier own message.

## What Makes This Cool

"Type real Waray/Taglish and nothing is touched, while an English typo in the
same box still gets fixed", and a report that proves it with two headline numbers from
replaying the user's own recent messages through the engine: Waray/Taglish
words changed and English typos fixed (more detail per layout below them). The export is very
likely the best conversational Waray/Taglish corpus there is: no public one
exists, and this one is usable precisely because it never leaves the machine.

## Constraints

- Fully local. Derived lexicons are never committed or shipped (D4).
- Messages are never stored whole. The encrypted store keeps only word counts,
  adjacent-pair counts and slip counts. Reports and logs carry counts only (the
  user chose: no example words).
- Every message-derived intermediate lives in one work directory,
  `$XDG_RUNTIME_DIR/correctiond-import/` (tmpfs, 0700, files 0600), so a crash
  never leaves chat text on disk, and is deleted by the pipeline (see Pipeline
  and cleanup). `run-import.sh` refuses to start when `XDG_RUNTIME_DIR` is unset
  or has under 1 GB free (eng review D3).
- Message tooling stays out of the shipped `.deb` (D7, which stands). D7's
  "keeps only the user's own messages" is revised by Premise 2: friends'
  messages may feed the local language lists.
- The engine re-validates every imported record and de-duplicates files by hash
  (existing).
- v1 lexicons stay ASCII-only (TODOS.md): accented tokens are rare in typical
  chat text, so this stays low priority.

## Premises

1. Rebuild the Tagalog/Waray lists from the whole export plus public Leipzig and
   OpenSubtitles lists, local-only, never shipped.
2. Friends' messages teach only the language lists. Personal never-corrected
   vocabulary comes only from the user's own messages. (Revises part of D7.)
3. Chat-inferred slips are filed per layout by evidence. (Revises D8, which
   allowed live fixes only. The user first chose "apply everywhere", then
   "decide by evidence" after the second opinion's challenge.) The evidence is
   corpus-level, because the export records no device per message (see step 6).
4. Imported words need a stricter bar than "seen twice", based on use count and
   number of chats (and, for the language lists, distinct senders), not letter
   distance. The report shows counts only; plaintext is deleted after import.

## Recommended Approach: B, chat-corpus pipeline plus replay check

(a "Learning" settings page; counts only, no example words).

### 1. Split: evaluation build, then production build

- The held-out set is the user's own messages from the last 3 months of the
  export.
- **Evaluation build:** every learned artifact is built without the held-out
  window: personal vocabulary, chat language lists and slips. Friends' messages
  from that window are excluded too, so no artifact has seen the test text.
- **Production build:** after the gate passes, all three artifacts are
  regenerated from the full export, including the held-out window, and that
  build is what gets imported. The recent months then reach personal vocabulary.

### 2. Replay evaluator (dev-only, built first)

- **Placement:** the engine crate gains a library target (`engine/src/lib.rs`)
  exposing only `EngineState`, `Action`, `Counters` and the lexicon loader that
  `main.rs` already uses; `ibus`, `persist`, `control` and every other module
  stay private (eng review D5).
  The evaluator is `engine/examples/replay.rs`, run with
  `cargo run --release -p engine --example replay`. Examples are not part of
  the `.deb`, so D7 holds. Replay drives the real `EngineState::on_key` path,
  with no re-implementation to drift.
- **Frozen learning:** `EngineState` gets a `learning: bool` (true in the
  engine, false in replay). When it is false, `learn()` and slip recording are
  no-ops. A unit test checks that a replay-mode state records nothing.
- **Input:** `heldout.tokens`, written by the converter in the work directory
  (0600): one held-out own message per line, its tokens joined by single spaces
  exactly as the converter split them, Messenger notices removed. Replay reads
  no JSON.
- **Engine state:** the real dictionary from the lexicon files under test. Each
  run happens twice:
  - lists only, with an empty personal store;
  - full, with the evaluation `personal.vocab.tsv` loaded.
- **Layouts:** the export records no device, so every layout the outputs will
  serve is replayed: `Qwerty` (the US variant), `Colemak` (the desktop variant)
  and `OskTap` (the on-screen keyboard). Each layout plants its own typos and
  is gated separately.
- **Context:** language context and the previous word reset at the start of
  every message, as for a new text field.
- **Labels,** frozen once before the baseline run and reused for every
  comparison:
  - EN: in the English list only;
  - FIL: in the pre-rebuild Tagalog or Waray list;
  - CHAT: held-out occurrences of the user's hand-labeled Waray, Tagalog or
    Bisaya words, the only labels a list rebuild can protect (whatever lists
    they are in);
  - SLANG: held-out occurrences of hand-labeled English slang and
    apostrophe-free English (dont, thats). No language list admits these, so
    they are reported in full mode only, where personal vocabulary protects
    them, and are not in the list gate;
  - OOV: everything else in no list;
  - hand-labeled typos and names are excluded from all rates.
- **Planted typos:**
  - every 10th EN token of 4 or more letters, in message order;
  - each gets one substitution with a neighbor on the replayed layout, chosen
    with a fixed seed (42);
  - so baseline and rebuild see exactly the same typos per layout.
- **Output** (`replay-<name>.json`, counts only, per layout and per mode):
  - CHAT changed-rate (lists-only and full): CHAT tokens changed, divided by
    CHAT tokens. This is the rate the rebuild exists to lower. Its lists-only
    baseline is expected well above 0, since these words are in no pre-rebuild
    list and lists-only mode has no personal store.
  - SLANG changed-rate (full mode only), which the personal import exists to
    lower.
  - FIL changed-rate: its baseline is expected near 0, since list words are
    never changed.
  - planted-typo fix rate;
  - OOV changed-count.

### 3. Converter v2 (`importers/messenger/`, Python stdlib only)

One pass over the extracted export, writing to the work directory:
- Repairs mojibake (existing) and skips Messenger notices: a template list, plus
  messages carrying attachments, calls, shares or an unsent flag.
- A standalone run of dots (`...`) breaks word-pair adjacency, as live typing
  does (TODO M13, eng review D4).
- Name filter, applied to every output: the lowercase parts of every
  participant name across all threads. Accepted tradeoff: real words that are
  also name parts (joy, grace) are dropped; the dropped count is reported.
- **Personal vocabulary** (`personal.vocab.tsv`, vocab v1, own messages only):
  - a `w` record when the word is used 3+ times in 2+ chats, or 10+ times in a
    single chat (so heavy one-chat words still count);
  - a `b` record under the same bar, dropping any pair containing a filtered
    token;
  - measured on the export: the record count is well under `MAX_RECORDS`
    (200,000).
- **Language lists** (`tl.chat.txt`, `war.chat.txt`, lexicon format, all
  senders):
  - Inputs: `data/en_words.txt` and the current `tl.txt` and `war.txt`.
  - A known word's primary language is the list where its per-million
    frequency is highest, including words shared by Tagalog and Waray or with
    English.
    The rule must match `Dictionary::primary_lang` (corelib/src/dictionary.rs);
    `data/primary-lang-vectors.tsv` is read by a corelib test and a converter
    unittest so the two cannot drift (eng review D6).
  - Each message with 2+ known words gets a label by majority primary language.
    Messages with ties or fewer known words get no label.
  - An out-of-list word takes the label it has in most of its labeled messages:
    - it needs a share of 60% or more;
    - English-majority words are not written to any list (they may still be the
      user's own words via personal vocabulary);
    - Bisaya words go to `war` by default (see Open Questions).
  - A word is kept only if 3+ distinct senders used it, in 2+ chats.
- **Bootstrap bias check:** the converter reports which language list each of
  the user's 50 hand-labeled words landed in. A Waray-labeled word that lands in
  `tl` counts as a mislabel.
- **Slip candidates** (`slips.vocab.tsv`, step 6, DEFERRED by eng review D1):
  own "*word" self-corrections only.
  - The candidate is a message that is exactly `*word` or `word*`.
  - The match is the previous own message in the same thread within 120
    seconds, containing a word one substitution away from `word`.
  - Excluded: the typed word passes the personal bar or is in any list.
  - Multi-word corrections are ignored.
  - The near-miss source is dropped: it is the same letter-distance test that
    mislabels real Waray words.

### 4. Lexicon rebuild and the gate

- `build-lexicon.py` gains a per-file format: `--freq FORMAT:PATH`, with FORMAT
  one of leipzig, plain or lexicon. The old `--freq PATH --freq-format F` keeps
  working.
- Rebuild command:
  `build-lexicon.py --lang war --freq lexicon:war.txt --freq lexicon:war.chat.txt --out war.new.txt`.
  Tagalog is the same, plus `--freq plain:tl_50k.txt` (FrequencyWords).
- Counts are summed raw. Chat words therefore keep a small relative frequency.
  That doesn't affect protection, since any list word is never corrected, only
  candidate ranking. The gate measures the choice.
- Then `clean-lexicon.py`, then a replay with the new lists.
- Output mode for all chat-derived lexicons and intermediates is 0600: both
  scripts gain `--mode`, defaulting to 0644 for public-only builds.
- **Typo share of admitted words:** a seeded random sample of 50 newly admitted
  list words is shown to the user locally for labeling. A typo share above 5%
  fails the gate. There is no automatic floor change or rerun; raising the
  sender floor is a manual rerun with `--sender-floor 5`.
- **Acceptance rule,** on the evaluation build, lists-only mode, every layout.
  This is the acceptance evidence:
  - CHAT changed-rate at most 5% absolute and at most half its baseline;
  - FIL changed-rate not above its baseline;
  - planted-typo fix rate no more than 1 percentage point below its baseline;
  - typo share of admitted words at most 5%.
- When the gate fails, the old lists stay installed. The run continues with the
  personal vocabulary import and cleanup (see Pipeline).
- **Production lists:**
  - The production build applies the same rules to the full export.
  - Words it admits beyond the evaluation lists (from the held-out window) get
    their own typo-share sample: min(50, count) words, the same 5% bound.
  - Replaying held-out text against production lists would be contaminated, so
    that sample is the production check.
  - Production lists are installed only if the evaluation gate and this sample
    both pass.
- After install, restart the engine (Settings, Restart engine; or
  `ibus restart`). The dictionary is built only at startup.

### 5. Engine: vocab v1 `s` records (DEFERRED by eng review D1; kept for a later follow-up)

Record: `s<TAB><layout><TAB><typed><TAB><intended><TAB><count>`.
- **layout** is one of `qwerty`, `colemak` or `osk`, mapping to
  `LayoutId::Qwerty`, `Colemak` and `OskTap`. There is no "all": the converter
  writes one record per layout.
- **typed** and **intended** are single ASCII letters. Readers lowercase them
  and skip the record when either is not a letter, or when they are equal.
- **count** is a positive integer, clamped to 1..=1,000,000; duplicates are
  summed.
- An unknown layout is skipped and counted, like any malformed record.
- `s` records count toward `MAX_RECORDS`.

Changes:
- `VocabBatch.slips` and `parse_vocab`;
- `LearnStore::add_imported` and `import_totals`;
- the persistence actor's import transaction (`DirtyBatch` already carries
  slips), so slips are written with the import record in one transaction;
- `docs/vocab-format.md`;
- tests: parse, store, and "an imported slip is persisted and restored after
  restart".

Imported slips follow the live rule: a slip is persisted only at count of 2
or more (`PERSIST_MIN`, as in `take_dirty`); a count-1 slip stays in memory
only. This is stated in `docs/vocab-format.md` and tested. A new D-Bus
method, `ImportVocabulary2(h) -> (u words, u pairs, u slips)`, sits beside the
unchanged `ImportVocabulary`. `engine import` prefers it and prints
`Imported N words, M word pairs and K slips.`.

### 6. Slips: decided by evidence (DEFERRED by eng review D1: the measured yield was too small, and the QWERTY-vs-Colemak test failed, so nothing would be imported)

- For every candidate pair, the miner records whether it is a key neighbor on
  QWERTY and on Colemak (`sub_cost` in `layout.rs`).
- Only pairs that tell the layouts apart count toward the test: Q are
  QWERTY-only neighbors, C are Colemak-only neighbors. 27 of QWERTY's 69
  neighbor pairs are also Colemak neighbors, so a raw "80% QWERTY" share could
  never pass.
- **Phone/QWERTY corpus:** Q at least 3 times C and at least 10. The Q pairs
  and the pairs that are neighbors on both are written under `qwerty` and
  `osk`; C pairs and neither-pairs are dropped.
- **Colemak corpus:** C at least 3 times Q and at least 10. The C pairs and
  both-neighbor pairs go under `colemak`; Q pairs and neither-pairs are
  dropped.
- **Otherwise** nothing is imported.
- The replay then runs, in full mode, under each layout that received slips,
  with and without them. They are imported only if that layout's planted-typo
  fix rate improves and its CHAT and FIL rates do not rise. Otherwise slip
  support (step 5) is deferred.

### 7. Pipeline and cleanup

One script, `importers/messenger/run-import.sh ZIP...`, extracts message JSON
from the export zips itself, so a rerun never depends on leftover plaintext.
- A `trap` on EXIT runs cleanup on every exit, success or failure, then checks
  that each deleted path is gone and reports any that remain.
- Hard errors abort: extraction, conversion, replay or `engine import` failing
  (for example a locked keyring). The trap still cleans up.
- A failed list gate is not a hard error. It skips only the list install, and
  the personal vocabulary import and the report still run.

Steps:
1. Extract message JSON from the zips into the work directory.
2. Convert (evaluation build).
3. Replay the baseline.
4. Build and clean the evaluation lists.
5. Replay the rebuild.
6. Label the typo-share sample, then gate.
7. Convert (production build).
8. Build and clean the production lists.
9. Label the production delta sample.
10. Import the production `personal.vocab.tsv` with `engine import`.
11. Install the production lists, if the gate and the delta sample passed.
12. Write the report.
13. Exit; the trap cleans up.

Files:

| File | Contents | Mode | Fate |
|---|---|---|---|
| `messenger-json/` (in the work directory) | extracted JSON | 0700 dir | deleted |
| `personal.vocab.tsv` (both builds) | own words and pairs | 0600 | deleted |
| `tl.chat.txt`, `war.chat.txt` | chat word counts | 0600 | deleted |
| `heldout.tokens` | held-out messages | 0600 | deleted |
| evaluation `tl.txt`/`war.txt` | candidate lexicons | 0600 | deleted |
| `replay-*.json` | counts | 0600 | merged into the report, then deleted |
| installed `tl.txt`, `war.txt` | production lexicons | 0600 | kept |

**Labels persist outside the work directory.** The Assignment labels and every
sample label live in `~/.local/share/correctiond/labels.tsv` (0600, one
`word<TAB>label` per line, label one of `war`, `tl`, `bisaya`, `slang`, `name`
or `typo`).
- The pipeline reads the file with `--labels` (default that path), adds each new
  sample label to it, and reuses it on reruns, so labels are frozen and never
  asked for twice.
- The EXIT trap never deletes it. `run-import.sh --forget-labels` removes it.

The current `~/Downloads/messenger-json/` from this session is removed by the
first run. The zips stay the user's to keep or delete.

### 8. Report

- **Writer:** the pipeline's final step.
  - It merges the converter stats, the replay JSONs and the engine's import
    reply into `~/.local/share/correctiond/import-report.json`.
  - The write is atomic (temporary file, then rename), mode 0600.
- **Schema:**
  - `imported_at`, `own_messages`, `threads`;
  - `words` and `pairs` imported;
  - `names_skipped`;
  - `gate`: `passed` or `failed`, plus `failed_checks`;
  - `lists_installed`: boolean;
  - `tl_added`, `war_added`: words in the installed production lists that were
    not in the previous lists, or 0 when `lists_installed` is false;
  - `replay`: for each layout (`qwerty`, `colemak`, `osk`) and each mode
    (`lists_only`, `full`), a `baseline` and a `rebuild` object, each with
    `chat_changed_rate`, `fil_changed_rate`, `typo_fix_rate` and
    `oov_changed_count`, plus `slang_changed_rate` in full mode;
  - `typo_share`: `evaluation` and `production_delta`.
- **"Learning" settings page:**
  - It reads the file and shows only these numbers. The headline pair, under
    the user's current layout and in full mode, is the CHAT changed-rate (Waray
    and Taglish words changed) and the planted-typo fix rate. The SLANG rate
    and the gate result sit below it.
  - A missing file shows "No chat import yet".
  - When GetStats `words_learned` is below the report's `words`, the page
    notes "Learned words were forgotten after this import".
  - Purge does not delete the report, which holds counts only.

## Out of Scope (v1)

Rerunning the same export is safe (eng review D7): converter v2 writes
byte-identical output for the same export, so the engine's SHA-256 duplicate
check refuses a second import, and `run-import.sh` treats that reply as done.
Still out of scope: re-importing a later export without double counting. File-hash dedupe stops
only identical files, and overlapping messages would be counted again. For v1,
re-import only after "Forget learned words". A per-thread watermark keyed by a
hash of the thread path is the likely v2 mechanism.

## Success Criteria

- After any run, successful or failed, every path the cleanup table marks
  "deleted" is gone, checked by the EXIT trap.

### R3-1 — feasibility (blocking)

**Problem**

> Persisting part of R2-2: the gate must measure tokens the rebuild can affect. CHAT includes hand-labeled slang, and the Problem Statement names apostrophe-free English (dont, thats, didnt) among the most-used missing words. Step 3 says English-majority out-of-list words 'are not written to any list'. So in lists-only mode, which is the only mode the acceptance rule uses, those CHAT tokens are unprotected in both baseline and rebuild. A list rebuild cannot lower their changed-rate. Inputs: let s be the share of CHAT occurrences that are English slang, and p the share of them the engine changes. Operation: the rebuild CHAT rate is at least s*p. Result: with s = 30% and p = 50%, the floor is 15%, above the 5% absolute bound, so the gate fails however good the Waray/Tagalog lists are. Words used by fewer than 3 distinct senders also can never enter a list.

**Remedy**

> Restrict CHAT, for the lists-only gate, to hand-labeled Waray/Tagalog/Bisaya words that are eligible for a list. Report slang and English-labeled words as a separate rate, measured in full mode (personal store), where the import can protect them. Or define the gate's CHAT rate over list-eligible words only, and say so in step 2, step 4 and The Assignment.

### R3-2 — consistency (blocking)

**Problem**

> Step 2 now makes the CHAT changed-rate the main gate number, reported per layout (Qwerty, Colemak, OskTap) and per mode (lists-only, full). Step 4 adds a production delta typo-share sample. A failed gate no longer aborts, so lists may not be installed. But the step 8 report schema still has only `baseline`/`rebuild` objects with `fil_changed_rate` and `typo_fix_rate`, one `typo_share`, and `tl_added`/`war_added`. It has no CHAT rate, no layout or mode dimension, no production sample result, and no field saying whether the lists were installed.
